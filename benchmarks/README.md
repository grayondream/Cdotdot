# CDD Performance Benchmarks

This directory is the reproducible performance baseline for the CDD compiler
(`TST-10`). It answers five questions:

1. **Runtime** — how fast is code generated by `cdd -O2` compared with the same
   program compiled by `clang++ -O2` and `g++ -O2`?
2. **Compile time** — how fast does `cdd` parse, optimize and emit objects,
   including a synthetic corpus that is large enough to be meaningful?
3. **Code size** — how large are the generated objects, LLVM IR, and
   executables (before and after stripping)?
4. **Memory** — what is the peak RSS of the compiled program and of the
   compiler itself?
5. **Optimization sensitivity** — how do representative workloads move across
   `-O0`, `-O1`, `-O2`, and `-O3` for all three compilers?

The baseline has two halves: the C++ references are the performance target, and
the CDD numbers are the current-state snapshot that future optimizations are
compared against. The baseline is a snapshot, not a target. Re-run it after
compiler changes and compare `benchmarks/results/*.json`; `BASELINE.md` is the
committed reference.

## Workloads

Each workload exists twice, with the same algorithm, data types and workload
size:

| Benchmark | Tier | What it exercises |
|---|---|---|
| `bench_fib` | core | recursive calls, branches, integer returns |
| `bench_sieve` | core | byte-array traffic, nested loops, branch prediction |
| `bench_matmul` | core | `float64` multiply-add, cache-friendly `i-k-j` order |
| `bench_nbody` | core | `float64` math, `sqrt`, pairwise force loop |
| `bench_sort` | core | recursive quicksort over 8M `int32` (LCG data) |
| `bench_hashmap` | core | open addressing, 8M inserts + 8M lookups |
| `bench_nqueens` | core | 13-queens backtracking, recursion, branch-heavy search |
| `bench_binary_search` | core | 2M binary searches over a 16M-element array |
| `bench_mandelbrot` | core | 1000×1000 `float64` escape-time, branchy FP |
| `bench_class` | core | 4M class objects, by-value method calls, field layout |
| `bench_str_append` | stdlib | owning `string` growth through repeated `append` |
| `bench_vec_push` | stdlib | `std::Vec<int32>` growth through repeated `push` |
| `bench_hashmap_std` | stdlib | `std::HashMap<uint32,int32>`, 4M puts + 4M gets |
| `bench_deque` | stdlib | `std::Deque<int32>`, 32M push_back/pop_front |
| `bench_malloc_churn` | alloc | 6M `malloc`/`free` pairs, scrambled free order |
| `bench_empty` | startup | empty process, loader/startup overhead |

- `core` isolates language and code-generation quality.
- `stdlib` also depends on the CDD standard-library implementation, so it is
  reported separately.
- `alloc` compares CDD's static mimalloc against the platform allocator used by
  the C++ reference. It is a product-level number, not an allocator contest.
- `startup` measures fixed process overhead and is not part of the core score.

Programs print a single checksum; the runner verifies that CDD and both C++
references produce the same output before timing. Floating-point benchmarks
compress their result into an integer so tiny reassociation differences do not
produce false failures.

## What the runner records

For every workload and implementation:

- median, min, max, p10, p90, standard deviation and coefficient of variation
  of the runtime samples;
- `perf` cycles, instructions, IPC, cache misses, branch misses, and effective
  GHz (`cycles / task-clock`);
- peak RSS;
- executable size before and after `strip --strip-all`.

For every compile source (benchmarks and the synthetic corpus):

- `-c -O2` median time, `-fsyntax-only` median time;
- object `.text`, `.rodata`, `.data`, `.bss`, debug and file size;
- LLVM IR bytes/lines for CDD and `clang++` (diagnostic);
- peak RSS of the compiler process.

The full run also adds an `-O0..-O3` matrix for six representative workloads
(`fib`, `matmul`, `nbody`, `hashmap`, `nqueens`, `str_append`).

## Compile-time corpus

`corpus/gen.py` emits deterministic `corpus_100`, `corpus_300`, `corpus_600`,
and `corpus_1200` files: N small functions with a loop plus a `main` that calls
every function. These files contain no imports and no interesting behaviour, so
the measurement is dominated by the front end, the optimizer and object
emission. They are generated into `benchmarks/.work/corpus/` and are not
committed. The report's `ms/fn` columns expose the marginal compile cost.

## Running

```bash
# Full baseline (5 warmups + 9 runtime runs; 1 + 5 compile runs;
# -O0..-O3 matrix; memory, IR and stripped sizes; corpus 100..1200)
python3 benchmarks/run.py --full --baseline-md

# Faster smoke run (3 runtime runs; corpus 300 only; no matrix/memory/IR)
python3 benchmarks/run.py --quick

# One workload
python3 benchmarks/run.py --only bench_matmul

# Force the optimization-level matrix in quick mode
python3 benchmarks/run.py --quick --matrix --matrix-levels 0,2

# Compare an optimization result against the committed baseline
python3 benchmarks/compare.py benchmarks/results/2026-11-18-fixed.json \
    benchmarks/results/2026-11-17-opt.json

# Fail if a core CDD/reference ratio regresses by more than 3%
python3 benchmarks/compare.py --fail-regression 3 \
    benchmarks/results/2026-11-18-fixed.json \
    benchmarks/results/2026-11-17-opt.json
```

Defaults:

- `cdd`: `build/bin/cdd` (override with `--cdd path/to/cdd`)
- C++ references: `clang++-22` (with the local libstdc++ path when needed) and
  `g++`; override with repeated `--cpp-compiler "cmd ..."`
- optimization: `-O2` for every compiler (`--opt`)
- debug info: C++ references are compiled with `-g` because CDD emits debug
  information by default
- CPU pinning: the least busy core is selected automatically at startup
  (`--cpu N` to pin a specific core, `--cpu none` to disable)
- outputs: `benchmarks/results/<label>.json` and `.md`

Useful switches: `--skip-matrix`, `--skip-memory`, `--skip-ir`,
`--skip-size`, `--skip-compile`, `--skip-corpus`, `--corpus-sizes`,
`--matrix-levels`, `--matrix-reps`.

Requirements: Python 3.10+, `taskset`, `strip`, and `perf` (optional; counters
are skipped automatically when unavailable).

## Reading the report

- `CDD/clang` and `CDD/g++` are **CDD time divided by reference time**.
  Values below `1.00x` mean CDD is faster.
- Tier geometric means aggregate the per-benchmark ratios; they are not an
  average of absolute times. `startup` is reported but is not part of the core
  score.
- The CV table shows run-to-run spread. Values above roughly 5% on this machine
  mean the cell needs a re-run before drawing conclusions.
- Compile time uses `cdd -c -O2` (front end + optimizer + object emission, no
  link) and the equivalent reference command. The `syntax` column is CDD's
  `-fsyntax-only` (which stops before semantic analysis) against the reference
  compiler's `-fsyntax-only` (which includes semantic analysis); it is a
  diagnostic split for CDD, not a fair cross-language ratio.
- Object `.text` measures generated code. `.rodata`/`.data`/`.bss` show static
  data; debug sections are not part of the loaded code size.
- Executable sizes include the runtime. CDD links mimalloc statically, so its
  executables are larger when the workload allocates; stripped sizes remove
  symbols and debug information.
- The `-O0..-O3` matrix separates gaps already present at `-O0` (front-end or
  codegen shape) from gaps that appear only after optimization.
- LLVM IR size is a diagnostic for CDD's own IR growth. The two front ends
  attach different metadata/debug information, so the IR ratio is not a strict
  cross-language code-size metric.

## Caveats

- The CDD compiler is built against LLVM 21 on the reference machine while
  `clang++` may be a newer LLVM release. `g++` provides an independent GCC
  reference.
- Baseline x86-64 only: no `-march=native`, no fast-math. Changing those flags
  changes the comparison and must be recorded as a separate baseline.
- The CPU governor is reported in every result. On a `powersave`/`schedutil`
  governor, boost behaviour adds noise; medians and pinning reduce but do not
  eliminate it.
- The baseline may be taken on a shared desktop. The runner records load
  average at start and end, auto-selects the least busy core, and interleaves
  implementations; use ratios and the CV table when the machine is busy.
- Runtime includes process startup and exit (typically 1–3 ms); the `startup`
  tier measures that overhead directly.
- `stdlib` rows combine code generation with the standard-library
  implementation. `std::HashMap`/`std::unordered_map` and
  `std::Deque`/`std::deque` have different growth strategies, so those rows are
  product-level comparisons.
- Peak RSS is sampled once per implementation; allocator caching and the static
  mimalloc arena make it sensitive to run order.
- Small benchmark sources are dominated by fixed compiler startup and the
  automatic `std.c` prelude. Use the `corpus_*` rows and `ms/fn` columns for
  compiler throughput.

## Adding a workload

1. Add `benchmarks/cdd/bench_NAME.cdd` with `module bench_NAME;`.
2. Add `benchmarks/cpp/bench_NAME.cpp` with the same algorithm and output.
3. Register `("bench_NAME", "core"|"stdlib"|"alloc"|"startup",
   "description")` in `BENCHMARKS` in `run.py`.
4. Optionally add it to `MATRIX_BENCHMARKS`.
5. Run `python3 benchmarks/run.py --quick --only bench_NAME`, confirm the
   checksum matches, then re-run the full baseline.

## Known CDD issues observed while building this baseline

These are recorded here because they constrain 64-bit benchmark code; they are
independent of the performance numbers and should be tracked/fixed separately:

- The 2026-11-18 `2026-11-18-fixed` baseline includes the `-O0` loop-local
  alloca and unsigned-widening-cast fixes. The older 2026-11-17 file still has
  O0 error cells and should only be used for historical comparison.
- The unsigned-widening cast defect (`uint8`/`uint32` values sign-extended by
  explicit casts) was fixed on 2026-11-18; the old baseline's benchmark code
  still avoided the path, so its runtime numbers are unaffected.
